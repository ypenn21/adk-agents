The Plan Swarm: Systems Architecture & Graph Engineering

Autonomous Multi-Agent Software Lifecycle Under Formal Graph Governance

Paradigm Architectural Tenets
  • State Machine Governance: Replaces unstructured chat loops with a formal spec → plan → execute → audit → commit finite state automaton.
  • Graph Engineering as Law: Topology, transitions, invariant contracts, and read/write scopes are compiled from a single authoritative graph.json.
  • Anti-Echo Quorum Gates: 3-lens partitioned skeptic panels running with default-to-reject postures, 2-of-3 majority voting, and asymmetric evidence.
  • Human-in-the-Loop Safeguards: Non-negotiable physical gates held at planning sign-off and git version control commits.
Core Invariant: The swarm communicates solely through versioned filesystem artifacts under plans/, passing file paths rather than prose summaries.

Why Unstructured Multi-Agent Systems Fail

Common Multi-Agent Anti-Patterns vs. Plan Swarm Remedies

Failure Mode Underlying Root Cause Plan Swarm Architectural Defense
Conversational Drift Prompts re-summarize past context; lossy LLM compression progressively degrades specifications. Artifact-Based Truth: Filesystem artifacts under plans/ serve as the sole source of truth. Agents receive absolute paths, never prose summaries.
Correlated Error & Echo Chambers Identical prompts to identical models produce correlated hallucinations masquerading as agreement. Lens Partitioning: Disjoint reading assignments, mandatory Asymmetry Tests, and cross-lens corroboration weighting.
Silent Shortcut Hallucination Agents fake green builds by deleting tests, commenting out assertions, or returning hardcoded literals. Anti-Shortcut Auditor: Independent static AST check at file:line + dynamic execution + automated scan for deferred work/gutted tests.

  • spec-deliberator: Generative multi-stakeholder consensus (Product, Engineering, Ops/Security).
  • plan-deliberator: Multi-territory trade-off solver (Intent, Codebase, Delivery pipeline).

Contract File-First Execution Rules
  • Zero Oral Re-summaries: Orchestrator passes concrete file paths to subagents. Re-summarizing plan steps in chat instructions introduces noise and model bias.
  • Legal Hierarchy: HTML visualizers (visual-spec.html, visual-plan.html) are purely derived projections. If they disagree with markdown, markdown always wins.
  • Git History Protection: The plans/audit/ directory contains an explicit .gitignore with *, ensuring dynamic logs do not pollute git history.
  • Resumable Artifact Trail: Every transition produces an immutable markdown record (e.g. -r2, -r3 on re-runs) for full post-mortem auditability.

Principle 2: Adversarial Partitioning & The Asymmetry Test

Overcoming LLM Correlated Errors Through Disjoint Attack Vectors

Spec Lenses spec-validator
  • Lens 1: Internal Consistency
    Checks the spec against itself; flags contradictory sections.
  • Lens 2: Missing Requirements
    Checks against external reality (nulls, concurrency, auth, limits, errors).
  • Lens 3: Malicious Compliance
    Games the acceptance criteria with the laziest useless implementation.
Plan Lenses plan-validator
  • Lens 1: Sequencing & DAG
    Checks dependency ordering and file mutation collisions.
  • Lens 2: Ground Truth
    Opens real repository files to verify functions, fields, and signatures.
  • Lens 3: Blast Radius
    Traces call sites, downstream consumers, and disturbed CI/CD tests.
Diff Lenses implementation-validator
  • Lens 1: Claim vs. Reality
    Verifies if the git diff matches commit/PR claims.
  • Lens 2: Failure Paths
    Probes error handling, resource leaks, and edge timeouts.
  • Lens 3: Blast Radius
    Hunts callers and contracts broken outside the immediate diff.
The Asymmetry Test: Before dispatching a panel, you must name at least one defect that only that specific lens could find. If a lens cannot be differentiated, it must be merged into a 2-agent panel to prevent false corroboration.

Principle 3: Deliberative Collaboration under Asymmetric Observability

Generative Consensus vs. Adversarial Rejection (arXiv:2607.06157)

Core Mechanics Deliberation Rules
  • Disjoint Context Bundles: Each delegate holds private evidence (e.g. user research vs. infra limits vs. compliance policies) that others cannot see.
  • Centralization Baseline: When all context fits in a single prompt window, centralized revision wins by up to +34 normalized reward. Deliberation is only used when context cannot be merged.
  • Verbatim Dialogue Relays: The orchestrator relays turn transcripts verbatim. Paraphrasing drops vital technical details and signatures.
  • Earned Acceptance: An acceptance without a verified justification against private territory is invalid, blocking sycophantic consensus.
  • Hard Bounded Rounds: Hard cap at 4 rounds max to guarantee termination.
Deliberator Panels Two Swarm Implementations

1. spec-deliberator:

  • Product Delegate: Holds customer journeys, ticket data, and business KPIs.
  • Engineering Delegate: Holds tech stack constraints, latency budgets, and API contracts.
  • Ops/Security Delegate: Holds ACLs, compliance policies, and telemetry specs.

2. plan-deliberator:

  • Intent Delegate: Defends spec.md acceptance criteria against scope cuts.
  • Codebase Delegate: Deep-reads subsystem ASTs, method signatures, and seams.
  • Delivery Delegate: Assesses CI execution, migrations, rollback safety, and runtime metrics.

Principle 4: TDD & Anti-Shortcut Verification

Enforcing Real Implementation Integrity

Feathers' Legacy Seam Protocol Engineer Contract
+-------------------------------------------------------------+
| 1. Locate Seam in existing code without changing logic      |
| 2. Break external dependencies using minimal structure      |
| 3. Write Characterization Test locking in legacy behavior   |
| 4. Execute Red -> Green -> Refactor micro-steps             |
| 5. Verify Build & Tests green on EVERY individual step      |
+-------------------------------------------------------------+
  • Honest Execution Groups: Tasks in a group execute in parallel (max 4). They must touch disjoint files. Colliding files force tasks into sequential groups.
  • Plan Checkbox Tracking: Engineers tick off [x] directly in plan.md, annotating the concrete file that received the change.
Anti-Shortcut Hunter Auditor Contract
  • Static Proof (file:line): Every step must cite the exact file and line range where the logic was implemented. Generic assertions result in a FAIL.
  • Dynamic Suite: Runs build and test suites once; captures exact stdout/stderr.
  • Anti-Shortcut Scan:
    • Flagging deferred work: TODO, FIXME, HACK, "in production...".
    • Flagging test sabotage: skipped tests (xit, @Ignore) or deleted assertions.
    • Flagging fake implementations: hardcoded return literals designed to cheat assertions.
  • Bounded Retry Loop: Capped at 3 rounds between engineer and auditor before escalating to human operator.

Skill Deep Dive: Phase 0 & Phase 1

Strategic Research, Specification & Adversarial Spec Gates

Phase 0 Strategic Research

Actor: starter / Research Agent

  • Maps the affected codebase surface before creating a milestone.
  • Produces plans/research/{topic}_context.md capturing architectural patterns, existing data contracts, and constraints.
  • Ensures product-owner builds upon real codebase realities.
Phase 1 Spec Deliberation (Optional)

Actor: spec-deliberator

  • Convened if requirements span multiple siloed stakeholder domains.
  • Enforces the Asymmetry Test; otherwise refuses and falls back to centralized revision.
  • Emits consensus-driven spec.md and deliberations/spec-deliberation.md.
Phase 1 Specification Authoring

Actor: product-owner (or visual-product-owner)

  • Runs the Socratic "Grill Loop" (≤3 questions/turn on limits, auth, errors).
  • Produces plans/active_milestones/{moniker}/spec.md with Given/When/Then acceptance criteria and updates 00-ROADMAP.md.
  • Visual variant renders zero-build visual-spec.html.
Phase 1 Gate Adversarial Spec Attack

Actor: spec-validator

  • Lenses: internal-consistency, missing-requirement, malicious-compliance.
  • Confirmed findings mandate concrete tightening edits to spec.md.
  • 1-vote findings triaged explicitly in spec-validation.md.
  • Majority quorum: 2-of-3 default (tunable to any-one for high-risk domains).

Skill Deep Dive: Phase 2 & Phase 3

Tactical Planning, Codebase Validation & Human Review Gate

Phase 2 Tactical Architecture & Planning

Actor: architect (or visual-architect)

  • Read-only on source. Inspects existing files, ASTs, and tests.
  • Emits plans/active_milestones/{moniker}/plan.md with parallel execution groups and micro-steps.
  • Visual variant produces interactive visual-plan.html.
  • Optional plan-deliberator: Reshapes plans across Intent, Codebase, and Delivery territories when open trade-offs (e.g. migration strategies) exist.
Phase 2 Gate Adversarial Plan Attack

Actor: plan-validator

  • Code-Grounded: Skeptics read actual repository source files to check assumptions against reality.
  • Lenses: sequencing, ground-truth, blast-radius.
  • Identifies the first_domino (earliest invalidating step).
  • Produces adversarial-reviews/plan-validation.md.
Phase 3 Human Review Gate 🛑: Execution stops. starter prompts: "Review spec.md, plan.md, and adversarial-reviews/. Approve to proceed." User must explicitly type "approve".

Skill Deep Dive: Phase 4 & Phase 5

Construction, Quality Auditing, Diff Attack & Release

Phase 4 Construction Execution & Polish
  • engineer (Fan-out ≤ 4): Implements tasks under strict TDD on disjoint files. Tracks checkboxes in plan.md. Never commits.
  • simplifier (Optional): Refines naming and reduces cognitive complexity with zero behavioral changes.
  • auditor: Verifies steps at file:line, executes test suite once, runs anti-shortcut scan. Emits AUDIT_[Plan].md. Max 3 rounds.
Phase 4 Gate & Release Diff Validation & Tagging
  • implementation-validator: Attacks git diff BASE..HEAD via claim-vs-reality, failure-paths, and blast-radius lenses. Outputs calibrated severities.
  • visual-implementation-recap: Generates visual-recap.html for human pre-commit inspection.
  • 🛑 Human Commit Gate: starter demands explicit user confirmation before executing git commit with verified SHA recorded in state.json.
  • Phase 5 Release: product-owner marks milestone "Shipped" and creates git tag.

Feedback Loops & Graph Cycles

Formalizing Dynamic Failure Recovery

Cycle Topologies Backward Edges
  feedback edges (cycles):
    spec-validator -> product-owner
      when: confirmed findings — fold in tightenings

    plan-validator -> architect
      when: confirmed findings — apply fixes · first_domino

    auditor -> engineer
      when: code failure — fix the failing task

    auditor -> architect
      when: plan failure — step is impossible

    implementation-validator -> engineer
      when: confirmed defects — fix at calibrated severity

    commit-gate -> engineer
      when: more groups remain — next execution group
Safety Guards Cycle Termination Invariants
  • The 3-Round Auditor Cap: The auditor ↔ engineer loop is tracked under groups[].audit_rounds in state.json. If a task fails 3 consecutive times, the loop automatically terminates and escalates the failure evidence to the human user.
  • Plan Infeasibility Escalation: When an auditor detects that a planned step cannot be executed due to codebase constraints, control cycles back to architect to revise the plan rather than forcing the engineer to improvise.
  • Immutable Versioned Re-runs: Validator re-runs append version suffixes (-r2.md, -r3.md) rather than overwriting history, preserving the delta between cycles.

Graph Engineering Principle 1: Declarative Topology

Treating the Swarm as a Formally Typed Directed Graph

Schema graph.json Definition
{
  "graph_version": "plan-swarm@2.1",
  "state_file": "plans/active_milestones/{moniker}/state.json",
  "node_kinds": {
    "entry": "Where a run begins. No skill.",
    "role": "A single agent doing the phase's work.",
    "panel": "Lens-partitioned fan-out with quorum join.",
    "deliberation": "Delegates with disjoint territories.",
    "human-gate": "Execution stops for human input.",
    "renderer": "Additive human-facing view.",
    "terminal": "Where a run ends."
  },
  "nodes": [ ... ],
  "edges": [ ... ],
  "gates": [ ... ],
  "invariants": [ ... ]
}
Benefits Why Graph Formalism Wins
  • Code as Topology: Swarm nodes, directed transitions, read permissions, and write restrictions are declared in JSON, not buried in prompt strings.
  • Strict Invariant Declarations:
    • Sole committer: Only starter declares git commit.
    • Source writers: Only engineer and simplifier declare <repo source> in writes.
    • Panel integrity: Every panel declares $N$ lenses matching prompt files.
  • Zero Drift: Markdown documentation and diagrams are compiled from graph.json via CI automation, ensuring documentation never drifts from reality.

Graph Engineering Principle 2: Declared State Machine

Deterministic State Tracking via state.json

Schema state.json Instance
{
  "graph_version": "plan-swarm@2.1",
  "run_id": "ms_checkout-redesign_0c41",
  "moniker": "checkout-redesign",
  "phase": "2.gate",
  "gates": [
    { "id": "plan-approval", "state": "pending" },
    { "id": "commit", "state": "not-reached" }
  ],
  "nodes": {
    "product-owner":   { "status": "done", "artifact": "spec.md" },
    "spec-validator":  { "status": "passed", "confirmed": 0, "single_vote": 2, "single_vote_triaged": true },
    "architect":       { "status": "done", "artifact": "plan.md" },
    "plan-validator":  { "status": "running" }
  },
  "groups": [
    { "id": "1", "tasks": { "1.A": "done" }, "audit": "passed", "committed": "a3f19c2" }
  ]
}
Eliminated Anti-Pattern No More Heuristic Inference
  • The Failure Mode: Resuming a milestone by listing directory files causes silent re-entry bugs — a validator that failed leaves plan.md on disk just as a passing one does.
  • The State vs. Payload Contract: Files under plans/ contain the payload; state.json is the index over them. Resumed runs read phase directly.
  • Explicit Skip Recording: If a gate is intentionally bypassed (e.g. Asymmetry Test fails on deliberator), it is marked status: "skipped" with a required reason. An unrecorded skip is indistinguishable from a pass.

Summary & Architectural Key Takeaways

Engineering Autonomous Swarms for Production Systems

Architectural Victories Core Design Principles
  • Topology as Code: Swarm execution is treated as a deterministic graph state machine, verified at compile time with static linters.
  • Filesystem Ground Truth: Chat is transient and lossy; versioned filesystem artifacts provide an immutable audit trail.
  • Partitioned Skepticism: 3-lens adversarial panels eliminate echo chambers and calibrate severity before code merges.
  • Generative Deliberation: Knowledge-asymmetric delegate panels solve complex trade-offs without round-1 sycophancy.
  • Human Sovereignty: Autonomy is safely bounded by non-negotiable human approval and commit gates.
